In order to build systems that facilitate or support end-user programming, it is generally easier if the API exposed to the user is essentially the same API used to build the system itself (or at least a significant subset thereof). This is because users will be endowed with the same capability and power as the system developers—they will be on level playing fields. This was one of the principles of Smalltalk, for instance.

This requires keen and early planning/design of the API, as well as regular efforts at maintaining documentation.

There is risk in exposing too much power to end users, and for security purposes some APIs may need to remain internal, but the greater the overlap, the greater the possibility to empower users.

This is one of the principles of Smalltalk.

From [End-User Programming](https://www.inkandswitch.com/end-user-programming.html) by Ink and Switch:

> Our finding here is that for a living system to work, the internal and external APIs need to be mostly the same.
